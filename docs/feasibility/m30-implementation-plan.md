## 1. Exact outcome

Demonstrate that an authenticated public API request travels through FastAPI, the TypeScript server, the installed VS Code companion and the maintained Cline task, then returns a verified result to an official SDK or named coding client. Show the native command, task/revision, output, control request/decision, and any actual file effect for the exact package fingerprints. The TypeScript server remains the owner of history, instructions, caller tools/results, estimates, quotas, credentials, routing and durable operation identity. Cline continues to execute the model and native actions.

M30 is an acceptance and integration milestone. Small repairs to existing public contracts and test tooling belong here when real clients expose a defect. A new model executor, replacement Cline runtime, desktop frontend, production TLS/OIDC configuration, distributable VSIX, and performance soak do not.

**No fixture-only pass:** M27 and M29 already have fixtures and bounded native evidence, but M30 needs the public provider and first-party requests to run through the real installed Cline route. Native caller tools are currently withheld. FR-26 and tool-using client support cannot pass by enabling that flag in a simulation fixture.

## 3. The client request-key gate

Every generation currently requires a caller-provided stable `Idempotency-Key`. A static key across different prompts conflicts; a new key for each retry can duplicate native work. The named-client spike must capture a normal request, timeout/retry, second distinct prompt and intentional identical new prompt. A supported client path must prove that the same logical request retains its key while distinct user submissions obtain distinct keys.

If a pinned client cannot do this through configuration, evaluate a **scoped gateway compatibility adapter** as an explicit contract amendment. It may allocate a durable request identity only when the client provides a trustworthy stable per-request identifier or another verifiable retry token. It must bind principal, session, normalized payload fingerprint and retention, reject changed-payload reuse, and preserve server-side deduplication. A time window or body hash alone cannot distinguish a retry from an intentional identical new prompt and is insufficient. A client patch/plugin is another option, provided its exact version and behavior are accepted as the named target. If neither solution is supportable, choose another named client; do not label an SDK or a one-off curl script as a named coding-client pass.

Keep credentials and keys out of traces. Use request IDs, HMAC or redacted digests for correlation. Default SDK retries are part of the test, not disabled to hide duplicate admission.

## 5. Native and API acceptance matrix

| Scenario | Public entry and observation | Required result |
| --- | --- | --- |
| Text and context | First-party prompt; OpenAI Chat/Responses; Anthropic Messages | Exact unique marker reaches Cline and returns committed text; second turn uses the same task with canonical full history; rewind/branch/hidden-context claims are explicit. |
| Current instructions | Change the current server instruction while preserving canonical history | Native prompt composition reflects the new instruction; old instructions are not carried as privileged current authority. |
| Image | Commit known-checksum PNG through first-party attachment route, reference it from both provider profiles | Exact committed image reaches native task; foreign/expired/wrong-MIME references fail before dispatch. |
| Tools and effects | Qualified caller-tool binding plus named tool-using client | Native model proposes schema-valid calls; only the caller executes them; one addressed success/error result continues the turn; no native duplicate effect. |
| Controls | First-party addressed question, approval allow/deny, cancellation | Signed request and decision IDs match; deny has no effect; cancellation and local takeover fence stale remote actions. |
| Estimates and limits | Count then generate with output cap; compare JSON/SSE | `sdc-text-v1` provenance and scope shown; public quota/deadline distinct from native settlement; no fabricated billing/native tokens or success terminal after error. |
| Retry/restart | Drop HTTP reply after admission, retry original key, restart gateway/server | Stable operation/generation ID and one native send; a changed payload with the key conflicts; a new key can intentionally create a later request when context permits. |
| Isolation | Concurrent principals, credentials, tasks, attachments and SSE | No cross-session read/control, alias leakage, call-result replay or shared task admission outside declared binding policy. |

For SSE, compare parsed official SDK accumulators with the first-party committed result and capture error EOF behavior. OpenAI Chat must finish with its documented chunks and `[DONE]`; Responses uses typed lifecycle events; Anthropic uses message/block/delta/stop events. Streaming remains terminal-buffered under the SDC profile. [Official OpenAI streaming guide](https://developers.openai.com/api/docs/guides/streaming-responses), [Anthropic streaming guide](https://platform.claude.com/docs/en/build-with-claude/streaming).

## 7. Completion and handoff

M30 passes only when both advertised provider profiles have a named, pinned real coding client on their declared feature subsets, official SDKs parse the native-backed results, and first-party desktop controls and failure/isolation cases have traceable native evidence. If a named client requires unsupported options or cannot safely identify retries, its profile remains unaccepted until fixed or a different client passes. If the Cline tool proposal cannot be qualified without native duplicate effects, caller-tool support remains blocked and M30 remains In Progress; do not convert that into a fixture pass.

M24 then owns signed/distributed packages, HTTPS/OIDC/proxy deployment and clean-user upgrade/rollback. M25 owns final user/maintainer guides against that deployment. M26 owns frozen release, latency/load and one-hour soak. The M30 result should identify exact accepted client settings and version fingerprints so those later milestones can reproduce the same claims.
