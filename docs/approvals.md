# Approval engine and permission ledger (M11)

`ApprovalEngine` is the shared, server-side decision path. Configure it with `ServerDatabase`, `AuthorizationService`, and an Ed25519 private signing key loaded from deployment secret storage. Configure the matching public key on both `createApiServer({ decisionPublicKey })` and the bridge's `createApprovalDecisionHandler`. No signing key belongs in this repository.

An authenticated owner submits `POST /v2/sessions/{sessionId}/approvals/{requestId}/decisions` with `decisionId`, `requestRevision`, `actionDigest`, `choiceId`, `grantedPermissions`, `policyRevision`, and an expiry no later than the request and no more than five minutes away. The engine locks the exact session/request revision and, in one transaction, checks reviewer authority, the active device/binding/lease, canonical action digest, offered choice, exact permission subset, expiry, and control-lane capacity. It records the winner, creates a device-bound signed assertion, records proposed grants as `pending`, and inserts `approval.decide` in the independent control lane. The 202 response says `decision_recorded`; it does not include the assertion and does not mean the app applied or executed the action. Identical retries return the recorded decision; another winner conflicts.

The bridge handler re-inspects the exact pending native request, validates the request and permission subset again, checks the signed assertion's session/device/binding/lease/turn/request/digest/choice/grants, creates a durable application attempt, and consumes the one-time assertion through the device-authenticated endpoint before calling `resolveApproval`. It returns `applied` only when the adapter supplies application evidence. `accepted`, uncertain outcomes, and interrupted attempts require reconciliation and are not repeated. Authenticated approval events and command acknowledgements update the separate server application state; execution remains represented by turn events.

Session and persistent scopes are disabled. Server-side request expiry changes pending records to expired but never claims a native permission was revoked. Proposed grants remain pending until native application is observed. A supported revoke is recorded as revoked only after adapter evidence; unsupported revocation is audited, and unknown outcomes remain unknown. Action/turn grants are retired when the corresponding turn reaches a terminal event.

Native adapters are not implemented by M11. `FakeAppAdapter` supplies simulated request, application, and execution evidence only. Signing-key rotation, production key storage, and real-app approval behavior remain integration/deployment work.
