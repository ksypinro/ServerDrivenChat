# Cline Connect (M21)

> **Current user instructions:** Start with the [M24/M25 beginner manual](guide/README.md). This document preserves its historical milestone/pin and implementation details; its old package names are not the current installation target.

The adopted Cline 4.1.22 `sdc-m21.3` development build (extension version 4.1.2203) exposes app-owned API 1.2. It adds `bridge_connect` and `bridge_disconnect` as discoverable sequential SDK tools in Cline's existing session. Their names use underscores for provider compatibility; the neutral wire operations remain `bridge.connect` and `bridge.disconnect`. The companion is version 0.3.0. Original M19/M20 packages and acceptance records remain preserved.

## Graphical setup

Install the reviewed development packages in the local VS Code host, then use **Cline Bridge: Configure Server**. Enter a local profile ID and HTTPS server origin, and choose permitted control categories. HTTP is accepted only for loopback development. Origins cannot contain paths, credentials, queries or fragments. Profiles are held in extension global state with settings sync disabled; workspace files and model messages cannot configure a server. Approval control requires the server's signing key in its authenticated handshake.

Configure the server's OIDC callback allowlist with the exact URI displayed after profile setup (`vscode://server-driven-chat.sdc-cline-bridge/auth` on stable VS Code). The extension uses the server-mediated PKCE start/exchange/refresh routes, opens the native browser sign-in and verifies callback state. Access/refresh tokens and device credentials are stored only in VS Code SecretStorage. Pairing confirmation secrets remain in memory. The profile/credential key includes the exact server origin so changing origins cannot reuse another server's credentials.

In an existing native Cline task, type **“Connect to my server and follow its instructions”**. The installed tool advertises configured profile IDs. It accepts only a profile ID and optional display label. The extension displays the exact server, task, workspace, host and control categories for local confirmation. On first use, sign in graphically, confirm the displayed pairing code as the authenticated server user, then separately allow the local device/task binding. Both confirmations are enforced by the server. Declining or changing origin aborts connection.

After the authenticated binding handshake and lease renewal succeed, Connect returns a bounded connected result without secrets. The extension owns HTTP/SSE subscriptions and durable SQLite inbox/outbox, not the model. The originating model turn may end; later server prompts reach the same task without returning to the composer. The existing M10 lease, command admission, output checkpoint/replay, durable dispatch and M11 signed approval handler remain the shared runtime. Native Cline permissions and OS prompts still apply.

## Origin and lifecycle

Tool origin is captured out of band from the pinned SDK session and tool-call identity. The patch checks that the SDK session ID, captured task object, session object and installation/host/window/workspace match. It rechecks after asynchronous graphical work and immediately before app mutation. Model arguments cannot specify URLs, callback addresses, task IDs, credentials, grants or reviewer identity. Missing SDK session/tool-call identity returns a rejection directing the user to graphical selection.

**Cline Bridge: Connect Current Task to Server** is an explicit graphical fallback. It selects a configured profile and captures the current native task generation before review; it does not pretend to be a model tool invocation. Repeating Connect for the same live profile/task binding returns `already_connected` without another listener or pairing. A different profile/binding requires disconnect and fresh local review. A local user prompt, task switch or reload retains the existing native takeover semantics and requires selection/consent again; pairing credentials alone do not silently restore a native binding.

**Cline Bridge: Connection Status** and the persistent status indicator expose listener state and selected task. **Cline Bridge: Disconnect** disables dispatch synchronously, stops subscriptions and detaches the exact binding locally; it also attempts authenticated server detach. A network failure cannot keep local delivery enabled. It does not cancel already running app work or revoke native permissions. Use the separate addressed cancellation control for that purpose. No credentials or native binding tokens enter model-visible results or SQLite.

## Developer verification

Run `npm run test:m21`, root build/lint/tests, and the disposable PostgreSQL tests with `M21_TEST_DATABASE_URL` set to the repository's loopback test service. Native fixtures prove races and runtime behavior; they do not prove live Cline acceptance.

The **Start/Finish M21 Acceptance Capture (Disposable Task)** commands are restricted to `/private/tmp/sdc-m19-vscode-probe`. Capture records the native SDK Connect origin/result, exact binding, loaded artifacts, listener state and protocol events; it never submits a prompt or skips consent. `scripts/m21-native-server.mjs` is a developer-only loopback fixture using the real PostgreSQL/HTTP/SSE API and a synthetic disposable identity provider. It waits for the initiating native turn to complete before enqueuing two harmless text instructions. The second omits the first marker to check continuity. Its sign-in is explicitly a disposable fixture, not evidence of a deployed OIDC realm.

Validate saved native/server traces with `node scripts/verify-m21-evidence.mjs evidence/M21/live-vscode.json`. Live acceptance passed on 2026-10-07: the native initial prompt invoked the SDK tool, graphical first-use sign-in and both pairing confirmations completed, the initiating turn ended, and two later server prompts returned the marker and continuity replies in the same task. Repeated graphical Connect returned already connected, and disconnect was observed locally and in the server. See the [verification](../evidence/M21/verification.json), [native capture](../evidence/M21/live-vscode.json), [server trace](../evidence/M21/server-live.json), [validation](../evidence/M21/native-validation.log) and [UI observations](../evidence/M21/native-observations.json). The developer identity page uses an explicit Return to VS Code link to avoid a custom-scheme redirect being blocked by its form CSP. Local VS Code and the exact adopted pin are the only supported host/version. M22's complete graphical approval/denial/question/stop/reconnect/takeover workflow subsequently passed on the unchanged native pin and companion 0.4.0; see [workflow acceptance](cline-workflow.md). M23 systematic hardening subsequently passed with companion 0.5.0; see [hardening/recovery](cline-hardening.md). Full upstream compilation, signing/publication, Antigravity and remote hosts remain separate gates.
