# Identity and authorization

M08 adds framework-independent server auth primitives in `server/src/auth/`; M09 will connect them to HTTP routes. The provider boundary supports the accepted Keycloak-backed OIDC authorization-code flow with PKCE for a public native client. Configure the exact issuer, client ID, API audience, and exact callback URI allowlist at server/app setup. The provider rejects non-HTTPS issuers/endpoints except loopback development, mismatched state/nonce/issuer/audience, unverified emails, expired or stale tokens, unknown algorithms/keys, and non-allowlisted callbacks. It validates `RS256` signatures against the issuer's JWKS and refreshes discovery/key caches every five minutes.

The authorization request uses random state, nonce, and an S256 PKCE verifier. The code exchange returns an ID token, API access token, optional refresh token, and access-token expiry. The ID token is used only for sign-in and must match the OIDC nonce. API authentication uses a separately validated access token whose `aud` includes the configured server API audience. The native companion stores the access/refresh token set in `KeychainCredentialVault`; Keychain generic-password items use `AfterFirstUnlockThisDeviceOnly`. No token is stored in PostgreSQL, SQLite, logs, or URLs. The test suite uses generated disposable RSA/Ed25519 keys and mocked discovery/JWKS endpoints; no Keycloak realm is configured or contacted.

An OIDC subject is linked to an internal user by exact `(issuer, subject)`, with a stable opaque user ID. Provider-verified principal objects are frozen and tracked in process-local weak sets; authorization methods reject fabricated objects. A production caller must construct the provider from trusted server configuration and call `completeOidcSignIn()` or `authenticateUserAccessToken()` after token verification; client-supplied user IDs/roles are never authorization input.

Device pairing has independent server and local consent steps. The local companion starts a five-minute pairing request and receives a one-time high-entropy display code plus a local-only confirmation secret. The authenticated user confirms the code once on the server; the local consent action must then confirm using its secret and explicit consent before the device becomes active. Wrong, expired, reused, unconfirmed, or declined pairings fail closed. Pairing codes and confirmation secrets are stored only as SHA-256 hashes. The local app must keep the confirmation secret in memory only until the pairing screen completes.

Device credentials are 256-bit random bearer secrets. The server stores only their SHA-256 hashes, expires them after 30 days by default, rotates one active credential atomically, and rejects revoked credentials on every authentication. Owner revocation disables the device, revokes its credential, and revokes active bindings. The companion stores returned credentials in Keychain; it must replace the old local token only after the new token has been durably stored.

Session ownership is derived from `sessions.owner_user_id`. The owner can view, prompt, approve, administer, and assign/revoke operator or viewer membership. Operators can view and prompt, but cannot approve or administer. Viewers can only view. Device principals are distinct from human principals and can act only on sessions with an active binding; they never receive reviewer authority.

Approval assertions are Ed25519-signed, short-lived (`<= 5 minutes`) values binding the authenticated reviewer, device, session, turn, active binding and lease generation, request ID/revision, canonical action digest, offered decision, exact granted permission subset, policy revision, and expiry. Issuance requires an owner role, an exactly pending stored approval, an offered choice, a grant subset, and an assertion expiry no later than the request expiry. The bridge verifier checks the signature, destination device, expiry, and identity shape. PostgreSQL records first consumption with unique assertion/decision/request keys, so duplicate or competing assertion use fails. The receiving side must still reconcile any uncertain native-app response.

PostgreSQL migration 002 owns OIDC identities, session roles, short-lived pairings, device credentials, and consumed assertions. Test with `M08_TEST_DATABASE_URL=<disposable PostgreSQL 17 URL> npm run test:m08`; the checked-in integration test uses the M06 loopback-only test service. The future pairing HTTP route must rate-limit invalid code attempts. M08 does not configure a live Keycloak realm, deliver HTTP endpoints, add graphical sign-in/pairing screens, or claim production app support; the route and UI integrations belong to later milestones.
