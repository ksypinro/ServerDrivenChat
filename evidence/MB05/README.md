## Outcome

The official Mods surface is a credible way to observe and affect a Claude Code
session from code loaded by Claude Code. It does not yet establish the safety
properties required for an SDC driver. In particular, an SDC prompt may wait until
Claude is idle, and the available official failure semantics permit a failed hook
to be skipped. We have not shown that an authorization failure, mod reload, or
lost SDC authority reliably prevents such a queued prompt from starting.

Therefore this checkpoint adds no Claude driver, no Claude qualification record,
and no production catalog entry. The existing Cline driver and its qualification
are unchanged. MB-05 is not complete.

## Evidence collected

- The isolated PluginLab installation contains `Anthropic.claude-code` version
  `2.1.296`; its manifest declares VS Code engine `^1.94.0`.
- The installed extension directory contains no generated Claude Mods TypeScript
  declarations. The public declaration file examined identifies itself as
  generated by version `2.1.277`, so it cannot be treated as the exact 2.1.296
  contract.
- Anthropic documents that Mods hooks run in the VS Code extension's chat panel.
  Mod-drawn panels are not available there.
- Anthropic documents that `$.prompt.submit` waits until the Claude session is
  idle before starting a turn. The SDC host must therefore retain control of its
  durable HTTP/SQLite bridge; the mod's buffered HTTP helper is not a replacement
  for the host's streaming and recovery path.
- Anthropic documents that a hook which throws or times out before calling
  `next` can be skipped. A `.catch` handler can return a refusal, but that handler
  can itself fail and then be skipped. This does not prove the hard execution
  fence required when SDC authority expires while a prompt is queued.
- The inspected public declaration describes session and turn events and session
  data, but its version does not match the installed extension. No exact-build
  discovery of the conversation identity, reset/resume behavior, prompt ordering,
  or cancellation contract has been made.
- The corrected read-only observer uses literal event registrations, as required by
  the exact runtime. Its strict validation passes; two tests cover redaction and
  local prompt continuity after observation failure.
- The earlier claim that only Claude 2.1.193 could validate the Mod was incomplete.
  The extension includes `resources/native-binary/claude`, which reports
  **2.1.296**. Use this executable; the older Homebrew executable is irrelevant.
- Three additional developer-only tests exercise refusal behavior in that exact

  This confirms that an ordinary Mod hook is insufficient as the sole fence.

- [Exact-build results and fingerprints](exact-build-check.json) record both strict

## Remaining primitive needed

The required native primitive is an execution-time, session-bound authorization
check whose failure refuses dispatch, or a revocable queued request whose
invalidation is guaranteed before execution. It must survive guard failure and
Mod unload/reload, with a native command/turn identity for reconciliation.
An SDC-side timer, preflight check, short lease, ordinary `.catch`, or merely
waiting for an idle event cannot supply that guarantee: execution may happen
later, and a failed native hook can be skipped. Keeping work in SDC until idle
reduces exposure but does not prove atomic admission to native execution.

The live IDE observation establishes session and turn identity for the tested
conversation and view-close boundary. It does not establish clear/resume/branch
coverage, remote-input attribution, durable output replay, or atomic fencing.
It cannot fix the demonstrated hook semantics. Before Phase B, obtain exact-build
supported evidence for an independent fence and run the queued-revocation test.
If that primitive is absent in 2.1.296, MB-05 cannot be completed under the pinned
version and existing-conversation constraints. No driver should be connected on
an assumption that the hook always succeeds.

## Unblock gate

Run a narrowly scoped evaluation in PluginLab with a disposable, user-selected
existing Claude conversation, using Claude Code 2.1.296 only. The candidate can be
added through Claude Code's own VS Code plugin panel from its local marketplace;
do not launch a separate CLI session. The user must review/accept the plugin in
the panel and enter any Claude sign-in credentials themselves. First obtain the
version-specific Mod declarations from that build and record complete installed
artifact fingerprints. Then test, without tools or workspace changes:

1. Identify the selected session with a stable native identity and detect clear,
   resume, branch, reload, logout, or replacement.
2. Send two attributed text prompts into that same existing session and correlate
   output and completion with each command.
3. Select another session and demonstrate refusal before any prompt enters it.
4. While Claude is busy, queue an SDC prompt, invalidate the SDC binding before
   Claude becomes idle, then prove that the prompt does not execute.
5. Repeat the authority test for lease expiry, local takeover, mod reload, host
   disconnect, hook timeout, thrown hook, and refusal-handler failure.
6. Establish whether native events and durable checkpoints allow honest recovery
   after a crash before submission and after submission but before acknowledgement.

The gate passes only if invalid authority cannot result in a native prompt effect,
including when hooks fail or the mod reloads. If the exact supported 2.1.296
interface cannot establish this, keep MB-05 In Progress and record the missing
vendor primitive. Do not work around the limitation with a separate Claude
process, private endpoint, extension patch, UI automation, or a newer extension.

## Implementation after the gate

Only after native evidence passes, add a Claude driver and an SDC-owned Claude Mod.
Keep session-local secrets short-lived and separate from server credentials. Bind
the local handshake to host/window/workspace and native session identity, reject
stale generations and redirects, and persist SDC command/event state in the
existing file-backed bridge. Implement only `probe`, `attach`, `inspect`, `submit`,
`subscribe`, and `detach`; keep optional controls unqualified. Treat any uncertain
native effect as reconciliation-required and never resubmit it blindly.

Then qualify the real REST/SSE route, recovery, local takeover and lease expiry,
plus the existing Cline regression subset. Sign a qualification only for complete
measured artifacts and the exact 2.1.296 build that passed. Production admission
and release remain MB-09.
